% ---------------------------------------------------------------------
% 1.1 Background

\section{Background}
\label{sec:background}

Digital filters are a core building block of embedded signal processing, used
to remove noise, shape frequency responses, and condition signals prior to
further analysis or control. Filter design is conventionally a two-stage
process: the filter is first evaluated offline in simulation (e.g.\ MATLAB),
and the resulting implementation is then transferred to target hardware for
verification. This separation makes it difficult to directly compare simulated
and measured behaviour during development, and it does not expose
implementation-specific effects such as fixed-point quantization, coefficient
scaling error, execution-time variation, and sampling jitter. A real-time
evaluation platform that observes the filter during on-target execution
addresses this gap.

% ---------------------------------------------------------------------
% 1.2 Problem Statement
% ---------------------------------------------------------------------

\section{Problem Statement}
\label{sec:problem_statement}

Evaluating a digital filter on embedded hardware is constrained by three
practical limitations:

\begin{itemize}
    \item \textbf{Lack of real-time observability:} filter output
          running on a microcontroller is not visible to the developer
          unless it is explicitly captured and transmitted to an external
          system.

    \item \textbf{Reconfiguration overhead:} changing the filter type
          or coefficients on a conventional setup requires firmware
          modification and re-flashing, interrupting the test-and-observe
          cycle.

    \item \textbf{No unified visualization layer:} even when signal
          data is captured, a lightweight mechanism for synchronized
          multi-channel visualization with runtime-adjustable display
          parameters (sample window, channel visibility) is typically
          unavailable.
\end{itemize}

% ---------------------------------------------------------------------
% 1.3 Objectives
% ---------------------------------------------------------------------

\section{Objectives}
\label{sec:objectives}

The project implements a Real-Time Digital Filter Evaluation Platform that:

\begin{enumerate}
    \item generates a known test signal and applies it to a digital filter under test,
          executed either locally or on a dedicated target microcontroller;
    \item acquires the resulting signals and streams them to a host computer without
          manual data retrieval;
    \item provides synchronized, browser-based visualization of the acquired channels
          with runtime-configurable display parameters.
\end{enumerate}

% ---------------------------------------------------------------------
% 1.4 Implemented Solution
% ---------------------------------------------------------------------

\section{Implemented Solution}
\label{sec:solution}

The platform is built around an ESP32-S3, which performs signal generation and
acquisition and acts as the network bridge. A separate Arduino Nano 33 IoT
target microcontroller optionally executes the digital filter under test.
Processed and acquired data are transmitted wirelessly via UDP to a Node.js
host bridge and forwarded to a browser-based interface over WebSocket. This
establishes a continuous development loop in which the signal is generated,
processed on real hardware, transmitted, and visualized without manual
intervention.

\chapter{System Design and Implementation}
\label{chap:methodology}

The evaluation platform combines an ESP32-S3 platform controller, an Arduino
Nano 33 IoT target microcontroller, real-time signal processing, an
inter-controller communication link, wireless telemetry, and a host-side
visualization system. The architecture supports both local execution of the
filter on the ESP32-S3 and external execution on the target microcontroller,
allowing the same platform to evaluate either implementation.

% ---------------------------------------------------------------------
% 2.1 System Architecture
% ---------------------------------------------------------------------

\section{System Architecture}
\label{sec:system_architecture}

The platform consists of two embedded controllers: the ESP32-S3, which provides
signal generation, control, telemetry, and communication functionality, and the
Arduino Nano 33 IoT, used as the external target for filter evaluation. The
overall architecture is shown in Figure~\ref{fig:block_diagram}.

\begin{figure}[H]
    \centering
    \includegraphics[width=\textwidth]{figures/block_diagram.png}
    \caption{Overall architecture of the real-time digital filter
        evaluation platform.}
    \label{fig:block_diagram}
\end{figure}

The two controllers communicate over a UART-based interface with dedicated
command and ready-handshake signals
(Section~\ref{sec:inter_controller_communication}), which allows the ESP32-S3
to control the target's operating state and exchange configuration data at
runtime. The ESP32-S3 encapsulates processed and acquired data in DSM packets
(Section~\ref{sec:dsm_telemetry}) and transmits them over UDP to the host
application, which provides real-time visualization
(Section~\ref{sec:host_visualization}).

% ---------------------------------------------------------------------
% 2.2 ESP32-S3 Platform Controller
% ---------------------------------------------------------------------

\section{ESP32-S3 Platform Controller}
\label{sec:esp32s3_platform}

The ESP32-S3 is the central platform controller. Its firmware is implemented
using ESP-IDF and FreeRTOS and performs:

\begin{itemize}
    \item test-signal generation,
    \item acquisition of analog signals,
    \item execution of the digital filter in internal mode,
    \item communication with the external target,
    \item collection of target-side signals in external mode,
    \item runtime filter and signal configuration,
    \item DSM packet generation, and
    \item wireless UDP telemetry transmission.
\end{itemize}

The firmware is organized around a timer-driven processing loop: a hardware
general-purpose timer generates the periodic sampling event, and the
application task performs signal processing after receiving the timer
notification. This keeps interrupt execution short and decouples the timing
event from the processing workload.

% ---------------------------------------------------------------------
% 2.3 Execution Modes
% ---------------------------------------------------------------------

\section{Execution Modes}
\label{sec:execution_modes}

The platform supports two runtime-selectable execution modes.

\textbf{Internal execution:} the ESP32-S3 performs the complete
signal-processing operation locally. On each timer event, the input is
obtained from the configured signal generator or the ADC, and the
selected digital filter processes the resulting sample
(Section~\ref{sec:esp32_internal_processing}).

\textbf{External execution:} the ESP32-S3 does not perform the filter
calculation. It instead coordinates the target microcontroller over
the inter-controller interface, synchronizing on a GPIO handshake and
sampling the target's analog output directly rather than receiving a
digital result over UART (Section~\ref{sec:external_target_processing}).

The mode is switched at runtime: selecting external execution stops the
internal ESP32-S3 processing timer, and reselecting internal execution restarts
it. The same platform infrastructure therefore supports both local and
target-side filter evaluation.

% ---------------------------------------------------------------------
% 2.4 Test Signal Generation
% ---------------------------------------------------------------------

\section{Test Signal Generation}
\label{sec:test_signal_generation}

The ESP32-S3 includes a configurable signal generator that provides
deterministic test inputs, operating at the configured sampling frequency and
supporting sinusoidal and impulse waveform modes. The default configuration
uses a 5~kHz sampling frequency and a 100~Hz simulation frequency, with the
default waveform set to impulse mode at amplitude 100 (both the ESP32-S3 and
target firmware boot with this default; the frequency parameter applies to sine
mode). Simulation input, frequency, amplitude, and waveform type are
runtime-configurable without firmware modification.

Analog acquisition uses \texttt{ADC\_UNIT\_1} at 12~dB attenuation and the
default ADC bit width. Channel 4 provides the primary input in both execution
modes; channel 5 is used only in external mode, wired to the target's DAC
output for direct analog readback of the filtered result
(Section~\ref{sec:external_target_processing}).

% ---------------------------------------------------------------------
% 2.5 Real-Time Sampling and Processing
% ---------------------------------------------------------------------

\section{Real-Time Sampling and Processing}
\label{sec:realtime_processing}

The processing framework operates at a nominal sampling frequency $f_s =
    5$~kHz, giving a nominal sampling period

\begin{equation}
    T_s = \frac{1}{f_s} = \frac{1}{5000} = 200~\mu\mathrm{s}.
    \label{eq:sampling_period}
\end{equation}

A hardware timer generates the periodic processing event. The timer alarm is
programmed for $200 - 2 = 198~\mu\mathrm{s}$ rather than the nominal
200~$\mu$s, a fixed 2-tick reduction that compensates for ISR scheduling
latency. The interrupt service routine performs only the minimum required
operation — notifying the application task that a new sampling event is
available — so that acquisition and filtering execute outside the ISR. For
internal execution, the resulting sequence is:

\begin{equation}
    \boxed{
        \text{Timer Event}
        \rightarrow
        \text{Input Acquisition}
        \rightarrow
        \text{Digital Filter}
        \rightarrow
        \text{Telemetry Generation}
    }
    \label{eq:internal_sequence}
\end{equation}

The measured execution time of the processing operation is recorded in the
telemetry packet as the \texttt{dt} field, providing visibility of
processing-time behaviour through the host interface.

% ---------------------------------------------------------------------
% 2.6 Digital Filter Implementation
% ---------------------------------------------------------------------

\section{Digital Filter Implementation}
\label{sec:digital_filter}

The platform supports eight filter configurations, selectable at runtime:
floating-point and integer variants of direct-form IIR, FIR, second-order
sections (SOS), and lattice-type filtering (LTC). The filter type is selected
via the runtime command interface
(Section~\ref{sec:runtime_filter_configuration}), which passes the
corresponding coefficient set to a common filter-initialization function shared
by all eight configurations.

The coefficient bank implements a Bessel low-pass filter with a nominal cutoff
frequency of 555~Hz at a 5~kHz sampling frequency, with both floating-point and
fixed-point coefficient representations available. The default configuration is
the floating-point IIR implementation.

Both the ESP32-S3 (internal mode) and the Arduino Nano 33 IoT (external mode)
acquire their input via a 12-bit ADC and center the result to a signed
representation using the same expression:

\begin{equation}
    x[n] = ADC[n] - 2048.
    \label{eq:adc_centering}
\end{equation}

The centred sample is passed to the selected filter:

\begin{equation}
    y[n] = \mathrm{Filter}\left(x[n]\right).
    \label{eq:filter_processing}
\end{equation}

The two execution paths differ downstream of the filter, as described below.

\subsection{Internal Processing (ESP32-S3)}
\label{sec:esp32_internal_processing}

In internal mode, the input sample (from the signal generator or ADC,
Section~\ref{sec:execution_modes}) is centred using Eq.~\ref{eq:adc_centering}
and filtered using Eq.~\ref{eq:filter_processing}. The input and filtered
samples are additionally converted to DAC-domain telemetry fields by reversing
the centring offset:

\begin{equation}
    \text{dac0} = x[n] + 2048, \qquad \text{dac1} = y[n] + 2048.
    \label{eq:internal_dac_domain}
\end{equation}

Both signed and DAC-domain representations, together with the processing-time
measurement, are stored in the telemetry structure. This path provides the
local reference against which the external target implementation is evaluated.

\subsection{External Target Processing (Arduino Nano 33 IoT)}
\label{sec:external_target_processing}

In external mode, the ESP32-S3 does not receive the filtered sample digitally.
It waits for the RDY line to fall, records the timestamp $t_\text{low}$, and
samples two ADC channels: channel 4, on the shared input line ($x[n]$), and
channel 5, wired to the target's analog DAC output, which yields the filtered
result $y[n]$ directly as an analog readback. The ESP32-S3 then waits for RDY
to return high, records $t_\text{high}$, and computes the target's per-sample
processing latency:

\begin{equation}
    dt = t_\text{high} - t_\text{low}.
    \label{eq:external_dt}
\end{equation}

Both channels are centred using Eq.~\ref{eq:adc_centering} before insertion
into the telemetry packet.

On the target itself, the Arduino Nano 33 IoT firmware implements a
timer-driven acquisition and processing architecture, independent of the
ESP32-S3's sampling instant: a hardware timer generates the sampling event, and
the main application loop executes the processing chain

\begin{equation}
    \boxed{
        \text{ADC}
        \rightarrow
        \text{Signal Centering}
        \rightarrow
        \text{Digital Filter}
        \rightarrow
        \text{DAC Scaling}
        \rightarrow
        \text{DAC}
    }
    \label{eq:external_sequence}
\end{equation}

After filtering (Eq.~\ref{eq:filter_processing}), the result is converted from
the signed 12-bit domain to the target's DAC output range, scaled while
preserving the signal midpoint and clipped to the valid range:

\begin{equation}
    \text{dac\_out} = \mathrm{clip}\!\left(
    \left\lfloor \frac{y[n]\cdot \text{DAC\_MAX}}{4095}\right\rfloor
    + \frac{\text{DAC\_MAX}}{2},\; 0,\; \text{DAC\_MAX}\right),
    \label{eq:external_dac_scaling}
\end{equation}

where $\text{DAC\_MAX}$ is the target's maximum DAC output code. This allows

\section{Target Operating States}
\label{sec:target_operating_state}

The target microcontroller uses command and ready signals to coordinate two
mutually exclusive states:

\begin{equation}
    \boxed{\text{Sampling State}}
    \qquad
    \boxed{\text{Configuration State}}
    \label{eq:target_states}
\end{equation}

In the sampling state, the target executes the timer-driven acquisition,
filtering, and DAC-update cycle. When a configuration command is received from
the ESP32-S3, the target disables the sampling timer, enters the configuration
state, and signals its state via the ready line. After the command is
processed, the target re-enables the sampling timer and resumes real-time
processing. This prevents configuration operations from executing concurrently
with the real-time filtering sequence. The exact handshake protocol
coordinating this transition is given in
Section~\ref{sec:inter_controller_communication}.

On receipt of a filter-selection command, the corresponding configuration is

configurations to be evaluated on the same hardware without a new firmware
build.

\section{Inter-Controller Communication}
\label{sec:inter_controller_communication}

The ESP32-S3 drives CMD (GPIO4, active-low, default high) and reads RDY (GPIO5,
pull-up, default high) from the target, over a secondary link (UART1, 115200
8N1). To issue a command, the ESP32-S3: waits for RDY low, drives CMD low,
delays 5~ms, transmits the newline-terminated command line over UART1, then
waits for RDY high before driving CMD back high:

\begin{equation}
    \boxed{
        \text{RDY Low}
        \rightarrow
        \text{CMD Low}
        \rightarrow
        \text{Command Transfer}
        \rightarrow
        \text{RDY High}
        \rightarrow
        \text{CMD High}
    }
    \label{eq:command_sequence}
\end{equation}

On the target, a falling CMD edge suspends the sampling timer and pulls RDY
low. RDY returns high once a complete line has been received and the UART has
been idle for 5~ms; the target resumes sampling once CMD returns high. This
interface is not part of the high-rate signal-processing loop; it coordinates
configuration and control between the two controllers.

\label{sec:dsm_telemetry}

The sequence identifier allows packet tracking at the receiver. Packet
integrity is provided by a 16-bit checksum computed as the bitwise XOR of all
16-bit words in the packet — despite the field name \texttt{crc16}, the
algorithm is an XOR checksum rather than a cyclic redundancy check. The DSM
packet is the common data representation between the embedded platform and the
host-side visualization system.

% ---------------------------------------------------------------------
% 2.11 UDP Telemetry Transmission
% ---------------------------------------------------------------------

\section{UDP Telemetry Transmission}
\label{sec:udp_telemetry}

Rather than transmitting each DSM packet as an individual UDP datagram, packets
are accumulated into batches of \texttt{UDP\_BATCH\_SIZE} = 100, prefixed by a
6-byte header (4-byte batch ID + 2-byte packet count), a size verified by a
compile-time assertion:

\begin{equation}
    \boxed{
        \text{Sampling}
        \rightarrow
        \text{DSM Packet}
        \rightarrow
        \text{Packet Batch}
        \rightarrow
        \text{UDP}
        \rightarrow
        \text{Host}
    }
    \label{eq:batch_sequence}
\end{equation}

Batching reduces per-datagram transmission overhead while retaining individual
sample information within each DSM packet. The sequence number and batch
identifier together let the host track the received telemetry stream and detect
dropped batches (Section~\ref{sec:real_time_visualization}).

% 2.12 Host-Side Visualization

\section{Host-Side Visualization}
\label{sec:host_visualization}

A Node.js-based host bridge receives the binary DSM telemetry over UDP and
forwards the decoded data to a browser-based interface over WebSocket:

\begin{equation}
    \boxed{
        \text{ESP32-S3}
        \rightarrow
        \text{UDP}
        \rightarrow
        \text{Node.js Bridge}
        \rightarrow
        \text{WebSocket}
        \rightarrow
        \text{Browser}
    }
    \label{eq:host_path}
\end{equation}

The browser displays discrete samples using a staircase representation rather
than an interpolated continuous line, preserving the discrete-time nature of
the signals and making sample-to-sample variation, jitter, quantization
effects, and limit-cycle behaviour more apparent. For each displayed signal,
the interface computes the minimum, maximum, average, and peak-to-peak range,
and separately displays the processing-time signal \texttt{dt\_us} for direct
visibility of timing behaviour.

\section{Filter Design Verification}
\label{sec:filter_design_verification}

The designed ninth-order Bessel low-pass filter was first verified in MATLAB
before implementation on the embedded platforms. The filter was designed for a
nominal cutoff frequency of $f_c=555$~Hz and a sampling frequency of
$f_s=5$~kHz.

The simulated magnitude response was evaluated to verify the required cutoff
frequency and overall frequency-domain behaviour. The measured $-3$~dB cutoff
frequency was

\begin{equation}
    f_g = 554.75~\mathrm{Hz}.
\end{equation}

The deviation from the specified cutoff frequency is therefore

\begin{equation}
    \Delta f =
    |555-554.75|
    = 0.25~\mathrm{Hz},
\end{equation}

corresponding to a relative deviation of

\begin{equation}
    \frac{0.25}{555}\times100
    = 0.045\%.
\end{equation}

The measured cutoff frequency is therefore well within the specified $\pm1\%$
tolerance.

The impulse-response analysis was additionally used to determine suitable
truncation limits for the finite-word-length FIR implementations. The resulting
coefficient decay was used to select the FIR lengths employed during the
real-time evaluation.

\section{Real-Time Filter Evaluation}
\label{sec:realtime_filter_evaluation}

The designed ninth-order Bessel low-pass filter was evaluated under real-time
conditions on both the ESP32-S3 platform and the Arduino Nano 33 IoT target
platform. The purpose of the hardware evaluation was to verify the functional
behaviour of the different filter realizations and to investigate
implementation-specific effects that may not be visible in the MATLAB
simulation.

The evaluated filter structures comprise floating-point and integer variants of
Direct Form~I IIR, SOS, LTC, and FIR implementations. The same filter
specification and test methodology were used for the different realizations.

The ESP32-S3 provides the reference real-time implementation for the platform,
while the Arduino Nano 33 IoT provides an independent target environment for
evaluating the filter implementation on a separate microcontroller.

A representative experiment using an impulse input is shown for the
floating-point Direct Form~I IIR implementation in
Figure~\ref{fig:iir_float_impulse}. The resulting response is consistent with
the expected transient behaviour of the designed low-pass filter.

\begin{figure}[H]

\section{Limit-Cycle Behaviour}
\label{sec:limit_cycle_behaviour}

Particular attention was given to finite-word-length effects in the integer
implementations. The Direct Form~I IIR integer realization exhibited persistent
limit-cycle oscillations for specific input amplitudes, with representative
cases observed around amplitudes of 200 and 850.

This behaviour results from quantization effects within the recursive feedback
structure. Although the corresponding floating-point filter is stable,
finite-word-length arithmetic can produce a residual quantization error that is
sustained by the feedback path.

In contrast, the tested SOS, LTC, and FIR integer implementations showed decay
towards zero after the excitation was removed for input amplitudes up to 2000.
Under the tested conditions, no persistent limit-cycle behaviour was observed
for these structures.

The real-time experiments therefore demonstrated that the filter structure and
numerical representation have a significant influence on the practical
behaviour of a digital filter. This effect would not be fully apparent from the
floating-point pole-zero analysis alone.

\section{Microcontroller Comparison}
\label{sec:microcontroller_comparison}

The real-time filter evaluation was performed on the ESP32-S3 and Arduino Nano
33 IoT. In addition to these two platforms, the Arduino Due and Teensy 4.1 were
considered as reference microcontroller platforms for comparison of
computational requirements.

The Arduino Nano 33 IoT was used as an external target platform for functional
real-time filter evaluation. The present evaluation does not use the Arduino
Due execution-time values as measurements of the Nano 33 IoT. Instead, the Due
and Teensy values provide a reference for understanding how the computational
requirements of the filter compare with other commonly used microcontroller
platforms.

For the ninth-order filter, the reference results for the Arduino Due show that
the absence of a hardware floating-point unit has a significant effect on
floating-point execution. The floating-point Direct Form~I IIR implementation
requires approximately $131~\mu$s, corresponding to approximately $66\%$ CPU
load at a $200~\mu$s sampling period. The integer SOS implementation requires
approximately $71~\mu$s, corresponding to approximately $36\%$ CPU load.

For comparison, the ESP32-S3 executes the same ninth-order realizations
substantially faster. The floating-point Direct Form~I IIR implementation
requires approximately $6.5~\mu$s, corresponding to $3.25\%$ CPU load, while
the integer SOS implementation requires approximately $5~\mu$s, corresponding

\section{Comparison of Real-Time Realizations}
\label{sec:realization_comparison}

The experimental results demonstrate two important aspects of real-time
digital-filter implementation: computational efficiency and numerical
robustness.

For floating-point arithmetic, the Direct Form~I IIR realization provides a
stable and computationally efficient implementation on the ESP32-S3. The
measured execution time of approximately $6.5~\mu$s represents only $3.25\%$ of
the available $200~\mu$s sampling period.

For integer arithmetic, the Direct Form~I IIR realization provides a slightly
lower execution time but exhibits quantization-induced limit-cycle behaviour
for specific input amplitudes. The SOS realization avoids this behaviour under
the tested conditions while maintaining a low execution time of approximately
$5~\mu$s on the ESP32-S3.

The results therefore demonstrate that computational speed alone is not
sufficient for selecting a filter realization. Numerical robustness and the
arithmetic representation must also be considered.

\section{Conclusion}
\label{sec:conclusion}

The developed Real-Time Digital Filter Evaluation Platform successfully
combines test-signal generation, embedded filter processing, telemetry
transmission, and real-time visualization.

The ninth-order Bessel low-pass filter met its specified cutoff frequency with
a deviation of only $0.045\%$. The different supported filter realizations were
successfully evaluated under real-time conditions on the ESP32-S3 and Arduino
Nano 33 IoT platforms.

The experiments demonstrated that floating-point Direct Form~I IIR provides a
stable and computationally efficient solution on the ESP32-S3. In contrast, the
integer Direct Form~I IIR implementation exhibited quantization-induced limit
cycles for selected input conditions. The SOS, LTC, and FIR integer
implementations showed improved numerical robustness under the tested
conditions.

The comparison with the Arduino Due and Teensy 4.1 further demonstrates that
the available arithmetic hardware has a direct impact on the suitability of a
filter realization for real-time operation.

Consequently, the selection of a digital-filter implementation cannot be based
solely on execution time. Filter structure, numerical representation,
finite-word-length behaviour, and the computational capabilities of the target
microcontroller must all be considered when selecting a realization for a
real-time embedded application.
